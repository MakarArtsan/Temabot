**Решения, которых не было в ТЗ явно:**
1. Опорная точка докачки — `max(tg_msg_id)` из БД, а не `state.last_msg_id`. БД не
   разойдётся с реальностью, даже если процесс упал, не успев обновить state.
   `state` пишется для админки как heartbeat.
2. В форумной группе сообщение, отправленное в тему без ответа кому-либо, имеет
   `reply_to_msg_id` = корень темы. Считать это ответом нельзя — вся тема склеилась бы
   в одну reply-цепочку и сломала сегментацию (§4.2). Такое сообщение пишется с
   `reply_to = NULL`, `topic_id = корень`.
3. `video_note` (кружок) размечается как `voice` — расшифровывать его надо так же.
4. `raw` хранится компактным слепком (флаги forwarded/pinned/views), а не целиком:
   полный raw на сотнях тысяч сообщений раздувает базу.
5. Фильтр `collect = true` сделан сразу (это шаг 10), потому что иначе коллектор
   пришлось бы переписывать. При пустой таблице чатов первый запуск заводит группу
   из `TG_GROUP_ID` и включает сбор — иначе процесс стартует вхолостую.
6. Пустой текст нормализуется в `NULL`: иначе `coalesce` в upsert затирал бы
   осмысленный текст пустой строкой.

## Сделано на шаге 4

- `src/collector/backfill.py` + `make backfill DAYS=30`: порции по 200 с паузой 1.5 с,
  прогресс в консоль, точка остановки в `state` после каждой порции.
- Флаги: `--days`, `--chat`, `--dry-run`, `--restart`.
- 13 тестов: размер порции и пауза, сдвиг offset, остановка по дате, короткая порция
  как признак конца истории, возобновление, пропуск уже пройденного чата, `--restart`,
  служебные сообщения, битое сообщение, dry-run.

**Решения, которых не было в ТЗ явно:**
1. История читается **от свежих к старым**. Если процесс прервут на середине, в базе
   окажется самое нужное для дайджеста, а не переписка месячной давности.
2. Вместо `iter_messages` используется `get_messages(limit, offset_id)`: он отдаёт готовый
   список, поэтому порция и пауза управляются точно, а весь запрос целиком оборачивается
   в `with_flood_retry`.
3. Точка остановки пишется **после каждой порции**, а не в конце: обрыв на 40-й порции
   не теряет предыдущие 39.
4. Пройденный до конца чат помечается `done` и повторно не грузится — нужен повтор,
   есть `--restart`.
5. Служебные сообщения («Вася добавил Петю») пропускаются: в дайджесте и поиске это шум.
6. Сообщение ровно на границе периода включается (сравнение строгое, `date < cutoff`).

**Решения, которых не было в ТЗ явно:**
1. **Чужим бот молчит.** Вежливый отказ подтвердил бы, что бот что-то знает о группе;
   по §9 этого достаточно, чтобы промолчать. Исключение — нажатие кнопки: там тишина
   выглядит как поломка, поэтому приходит всплывающее «доступно только владельцу».
2. **Отправка в Telegram — HTML, а не Markdown.** Разметка Telegram ломается на любой
   звёздочке или подчёркивании внутри текста от модели; в HTML экранируется ровно три
   символа. Markdown остался для хранения и будущей админки — оба формата строятся из
   одних данных.
3. **В `digests.topics` теперь лежит вся структура дайджеста**, а не только список тем.
   Иначе `/digest <дата>` за прошлый день не смог бы собрать ту же картинку.
   Старые записи со списком тем читаются по-прежнему.
4. **Длинные сообщения режутся по границам абзацев** — Telegram не принимает больше
   4096 символов, а дайджест активного дня их перебирает.
5. `misfire_grace_time` и `coalesce` у задачи: после простоя дайджест всё равно уйдёт,
   но один раз, а не столько, сколько запусков пропущено.

**Что нашёл живой прогон (тесты не ловили):**
- `/who` падал: asyncpg выводил тип параметра как текст в `($3 || ' days')::interval`.
  Заменено на `make_interval(days => $3)`, добавлены тесты на все запросы команд.
- `/search` и `/stats` показывали время в UTC, хотя сутки считаются по Камчатке —
  пользователь видел вчерашний вечер вместо утра. Теперь время в таймзоне из конфига.

**Замеры на настоящей модели:**

| Настройка | Токенов на размышления | Всего выходных |
|---|---|---|
| по умолчанию | 340 | 382 |
| `reasoning_effort=low` (как в ТЗ) | 223 | 264 |
| `LLM_THINKING=disabled` | 0 | 39 |

Дайджест дня из 14 сообщений: 2058 входных и 501 выходной токен, около $0.0003.

**Решения и находки:**
1. **`deepseek-flash` — reasoning-модель.** В режиме строгого JSON размышления съедали
   весь лимит токенов, и ответ приходил **пустым**. `thinking: disabled` убирает их
   полностью — это и в десять раз дешевле, и надёжнее. Поставлено по умолчанию.
2. **У DeepSeek нет эндпоинта эмбеддингов** (404). Добавлены отдельные
   `EMBED_BASE_URL` / `EMBED_API_KEY`, чтобы векторы можно было брать у другого
   провайдера. Локальная `bge-m3` проверена: 1024 измерения, как в схеме.
3. **Индекс `ivfflat` из ТЗ заменён на HNSW.** ivfflat требует обучения на данных: пока
   чанков меньше числа списков, векторный поиск возвращает пустоту — ровно в первые
   дни работы. HNSW работает с первой строки. Применено и в схеме, и на боевой базе.
4. **Полнотекстовый поиск по чанкам соединяет слова через ИЛИ.** С `websearch_to_tsquery`
   вопрос «сколько стоит генерация ролика» не находил обсуждение с «12 рублей за ролик»,
   потому что требовались все слова сразу. Для `/search` (поиск по ключевым словам)
   строгий режим оставлен.
5. **Разметка тредов идёт от данных, а не по скользящему окну.** Первая версия брала
   «последние 3 дня от сегодня» — после бэкфилла 30 дней истории в поиск попали бы
   только последние сутки. Нашлось на сквозном прогоне: индексировался 1 тред из 3.
6. **Перехлёст чанков гарантирует хотя бы одно сообщение.** При жёстком бюджете в 250
   символов реплика длиннее бюджета давала нулевой перехлёст, и ответ на границе окна
   терялся для поиска.
7. Если эмбеддинги недоступны, поиск **деградирует до полнотекстового**, а не отказывает.

## Приватность БД (сделано попутно)

Supabase по умолчанию отдаёт таблицы схемы `public` через PostgREST под ролями
`anon`/`authenticated`, то есть по publishable-ключу, который публичен по своей природе.
Для базы с перепиской закрытой группы это прямое нарушение TZ §9. В `schema.sql` добавлен
блок: RLS без политик на всех 14 таблицах + снятие грантов у публичных ролей (блок
пропускается на обычном Postgres, где таких ролей нет). Проверено на живом проекте:
REST отвечает `401 permission denied` и на чтение, и на запись; 60 тестов приложения
