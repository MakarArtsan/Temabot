**Решения, которых не было в ТЗ явно:**
1. Опорная точка докачки — `max(tg_msg_id)` из БД, а не `state.last_msg_id`. БД не
   разойдётся с реальностью, даже если процесс упал, не успев обновить state.
   `state` пишется для админки как heartbeat.
2. В форумной группе сообщение, отправленное в тему без ответа кому-либо, имеет
   `reply_to_msg_id` = корень темы. Считать это ответом нельзя — вся тема склеилась бы
   в одну reply-цепочку и сломала сегментацию (§4.2). Такое сообщение пишется с
   `reply_to = NULL`, `topic_id = корень`.
3. `video_note` (кружок) размечается как `voice` — расшифровывать его надо так же.
4. `raw` хранится компактным слепком (флаги forwarded/pinned/views), а не целиком:
   полный raw на сотнях тысяч сообщений раздувает базу.
5. Фильтр `collect = true` сделан сразу (это шаг 10), потому что иначе коллектор
   пришлось бы переписывать. При пустой таблице чатов первый запуск заводит группу
   из `TG_GROUP_ID` и включает сбор — иначе процесс стартует вхолостую.
6. Пустой текст нормализуется в `NULL`: иначе `coalesce` в upsert затирал бы
   осмысленный текст пустой строкой.

- `src/collector/backfill.py` + `make backfill DAYS=30`: порции по 200 с паузой 1.5 с,
  прогресс в консоль, точка остановки в `state` после каждой порции.
- Флаги: `--days`, `--chat`, `--dry-run`, `--restart`.
- 13 тестов: размер порции и пауза, сдвиг offset, остановка по дате, короткая порция

  служебные сообщения, битое сообщение, dry-run.

**Решения, которых не было в ТЗ явно:**
1. История читается **от свежих к старым**. Если процесс прервут на середине, в базе
   окажется самое нужное для дайджеста, а не переписка месячной давности.
2. Вместо `iter_messages` используется `get_messages(limit, offset_id)`: он отдаёт готовый
   список, поэтому порция и пауза управляются точно, а весь запрос целиком оборачивается
   в `with_flood_retry`.
3. Точка остановки пишется **после каждой порции**, а не в конце: обрыв на 40-й порции
   не теряет предыдущие 39.
4. Пройденный до конца чат помечается `done` и повторно не грузится — нужен повтор,
   есть `--restart`.
5. Служебные сообщения («Вася добавил Петю») пропускаются: в дайджесте и поиске это шум.
6. Сообщение ровно на границе периода включается (сравнение строгое, `date < cutoff`).

**Решения, которых не было в ТЗ явно:**
1. **Чужим бот молчит.** Вежливый отказ подтвердил бы, что бот что-то знает о группе;
   по §9 этого достаточно, чтобы промолчать. Исключение — нажатие кнопки: там тишина
   выглядит как поломка, поэтому приходит всплывающее «доступно только владельцу».
2. **Отправка в Telegram — HTML, а не Markdown.** Разметка Telegram ломается на любой
   звёздочке или подчёркивании внутри текста от модели; в HTML экранируется ровно три
   символа. Markdown остался для хранения и будущей админки — оба формата строятся из
   одних данных.
3. **В `digests.topics` теперь лежит вся структура дайджеста**, а не только список тем.
   Иначе `/digest <дата>` за прошлый день не смог бы собрать ту же картинку.
   Старые записи со списком тем читаются по-прежнему.
4. **Длинные сообщения режутся по границам абзацев** — Telegram не принимает больше
   4096 символов, а дайджест активного дня их перебирает.
5. `misfire_grace_time` и `coalesce` у задачи: после простоя дайджест всё равно уйдёт,
   но один раз, а не столько, сколько запусков пропущено.

**Что нашёл живой прогон (тесты не ловили):**
- `/who` падал: asyncpg выводил тип параметра как текст в `($3 || ' days')::interval`.
  Заменено на `make_interval(days => $3)`, добавлены тесты на все запросы команд.
- `/search` и `/stats` показывали время в UTC, хотя сутки считаются по Камчатке —
  пользователь видел вчерашний вечер вместо утра. Теперь время в таймзоне из конфига.

**Замеры на настоящей модели:**

| Настройка | Токенов на размышления | Всего выходных |
|---|---|---|
| по умолчанию | 340 | 382 |

Дайджест дня из 14 сообщений: 2058 входных и 501 выходной токен, около $0.0003.

**Решения и находки:**
1. **`deepseek-flash` — reasoning-модель.** В режиме строгого JSON размышления съедали
   весь лимит токенов, и ответ приходил **пустым**. `thinking: disabled` убирает их
   полностью — это и в десять раз дешевле, и надёжнее. Поставлено по умолчанию.
2. **У DeepSeek нет эндпоинта эмбеддингов** (404). Добавлены отдельные
   `EMBED_BASE_URL` / `EMBED_API_KEY`, чтобы векторы можно было брать у другого
   провайдера. Локальная `bge-m3` проверена: 1024 измерения, как в схеме.
3. **Индекс `ivfflat` из ТЗ заменён на HNSW.** ivfflat требует обучения на данных: пока
   чанков меньше числа списков, векторный поиск возвращает пустоту — ровно в первые
   дни работы. HNSW работает с первой строки. Применено и в схеме, и на боевой базе.
4. **Полнотекстовый поиск по чанкам соединяет слова через ИЛИ.** С `websearch_to_tsquery`
   вопрос «сколько стоит генерация ролика» не находил обсуждение с «12 рублей за ролик»,
   потому что требовались все слова сразу. Для `/search` (поиск по ключевым словам)
   строгий режим оставлен.

## Расшифровка силами Telegram Premium

У аккаунта коллектора есть Premium, а значит Telegram расшифровывает голосовые сам.
Через MTProto это метод `messages.transcribeAudio`.

- `src/media/telegram_asr.py` — запрос расшифровки, ожидание результата (Telegram
  сначала отвечает `pending`, текст досылает позже), обработка отказов.
- Очередь пробует Telegram **до скачивания файла**: при удаче не тратятся ни трафик,
  ни диск, ни процессор.
- `ASR_PROVIDER`: `auto` (Telegram, иначе whisper), `telegram` (только Telegram),
  `local` (как раньше). По умолчанию `auto`.
- Отсутствие Premium запоминается на процесс — иначе каждое голосовое стоило бы
  лишнего запроса и отказа.
- Записи длиннее `TELEGRAM_ASR_MAX_SEC` (180 сек) даже не отправляются.
- В статистике очереди появились `by_telegram` и `by_whisper` — видно, кто считает.
- 17 тестов: удачный путь, ожидание `pending`, отсутствие Premium, исчерпанный лимит,
  FloodWait, слишком длинная запись, бесконечное ожидание, режим `telegram` без whisper.

**Почему это важнее, чем кажется:** на тарифе Amvera локальный whisper — это 1.6 ГБ
ОЗУ и несколько минут счёта на каждое длинное голосовое. С Premium коллектору хватает
минимального тарифа, а расшифровка появляется за секунды.

## Проверка перед запуском (сделано)

Весь код прошёл повторное ревью на «зальём на Amvera, введём секреты — заработает ли».
Нашлось и исправлено:

- **`/ask` и поиск молчали бы всегда.** В образе нет `sentence-transformers`, при
  `EMBED_BACKEND=local` индексатор падал на эмбеддингах и пропускал тред целиком —
  таблица `chunks` оставалась пустой, а полнотекстовый поиск тоже идёт по ней. Теперь
  чанки сохраняются без вектора (поиск по ним полнотекстовый), а когда эмбеддинги
  появятся, индексатор сам дошьёт векторы (`repo.get_threads_without_embeddings`).
- **Недействительная сессия.** `client.start()` на сервере пытался спросить телефон
  через `input()` и падал с `EOFError`. Теперь `connect()` + `is_user_authorized()` и
  понятная ошибка «перегенерируй TG_SESSION_STRING».
- **Копировщик замолчал бы после деплоя.** Новая строка группы появлялась с
  `copier='ask'` и `digest=false`. Теперь `repo.bootstrap_primary_chat(TG_GROUP_ID)` в
  collector и bot: если строки нет — сразу сбор, дайджест и копировщик включены; если есть —
  флаги владельца не трогаются.
- **История заливается сама.** `BACKFILL_DAYS=7` (по умолчанию): collector при первом
  старте проходит историю за 7 дней, прогресс в `state`, повторно не читает; ошибка
  заливки не валит сбор. `BACKFILL_DAYS=0` — выключить. Ручной `make backfill` тоже
  теперь по умолчанию 7 дней.
- **Время по умолчанию — Москва**: `TZ=Europe/Moscow` (было `Asia/Kamchatka`).
- +12 тестов (всего 452).

## Одно приложение на Amvera (сделано)

Владелец попросил не заводить три проекта. Теперь `APP_ROLE=all` по умолчанию:
`src/supervisor.py` накатывает схему, запускает bot, web и collector **отдельными
процессами** и перезапускает упавший с паузой 5 с → … → 5 мин (после 10 минут
нормальной работы пауза сбрасывается). По SIGTERM гасит всех: сначала SIGTERM, через
15 с — SIGKILL.

- Процессы, а не задачи в одном event loop: протухшая сессия коллектора не должна
  ронять админку, через которую её чинят. Цена — ~100 МБ памяти (замерено: ~300 МБ на
  три процесса против ~215 МБ в одном).
- Часть без своих переменных не запускается вовсе (с понятной строкой в логе), а не
  падает по кругу: без `TG_SESSION_STRING` работают бот и админка.
- `DB_POOL_SIZE=4` на процесс, если владелец не задал своё: Session pooler Supabase
  пускает 15 клиентов на базу, по 10 на процесс было бы 30.
- `SERVICES=bot,web,collector` — что запускать; healthcheck образа для `all` — `/healthz`.
- Роли `bot`/`web`/`collector` остались: при желании три проекта по-прежнему возможны.
- Проверено вживую и в собранном образе: без `APP_ROLE` стартует роль `all`, схема →
  web → `/healthz` 200 (и `HEALTHCHECK` образа), недостающие части пропущены с
  пояснением в логе; `docker stop` — остановка за секунду с кодом 0 (супервизор как
  PID 1 сам ловит SIGTERM). Бот при этом схему повторно не накатывает
  (`MIGRATE_ON_START=false` от супервизора): иначе его ALTER мог столкнуться с первыми
  запросами коллектора.
- 13 тестов на настоящих маленьких процессах: план запуска, перезапуск, остановка во
  время паузы, SIGKILL упрямому процессу, порядок «сначала схема».

## Публикация дайджеста в группу (сделано)

Решение владельца (TZ §9 дополнен): сначала смотреть самому, потом включить
автопубликацию раз в сутки. Колонка `chats.publish`: `off` (по умолчанию) | `manual` |
`auto`; у дайджеста — `published_at` и `published_msg_ids`.

- `src/digest/publish.py`: публикация только в ту же группу, без кнопок оценки, без
  звука (вечер); «Герои дня» с именами — только при включённом «Рейтинге недели».
  Пустой день не публикуется. Отметка ставится атомарно до отправки — кнопка и
  автопубликация не выложат дважды; пересборка дня отметку не снимает. Неудача до
  первого сообщения снимает отметку (можно повторить), после — оставляет (иначе дубль).
  «Убрать из группы» удаляет посты (Telegram разрешает боту первые 48 часов).
- Бот: в режиме «по кнопке» после вечерней сборки и после `/digest` — кнопка
  «📢 Опубликовать в группе» с подтверждением «Точно?»; в режиме «авто» — публикация
  и ссылка на пост владельцу. Кнопки только у владельца. `/groups` показывает режим.
- Админка: «Группы» — режим публикации и «Рейтинг недели» (с подтверждением,
  страница переделана в карточки — на телефоне таблица не помещалась); «Дайджесты» —
  колонка «В группе», внутри — «Так его увидит группа», кнопки опубликовать/убрать.
- `BOT_API_URL` — адрес Bot API для бота и админки; проверка шла через подставной
  сервер на localhost: в него ушло одно сообщение в id группы, без звука и без
  кнопок, «убрать» удалило именно его. В живой Telegram ничего не отправлялось.
- 22 теста публикации + 9 тестов админки (всего в проекте 496).

## Запуск, который не падает молча (сделано)

На Amvera контейнер дважды не поднимался с пустыми логами. Найдено в собранном образе:
при недоступной базе админка ждала подключения на старте (lifespan), uvicorn не
открывал порт 80 — хостинг считал запуск проваленным. Исправлено:

- админка открывает порт сразу, пул к базе — лениво; `/healthz` ждёт базу не дольше 5 с,
  подключение asyncpg — не дольше 15 с (было 60);
- супервизор запускает web первым, bot и collector — после схемы;
- при неверном значении переменной — читаемое сообщение (без самих значений), а при
  «запускать нечего» процесс не выходит, а ждёт и раз в 5 минут повторяет причину:
  при мгновенном выходе Amvera перезапускает контейнер по кругу и лог теряется;
- первая строка лога — `Запускаю роль: …` с временем, до любых других действий.

Проверено в собранном образе: база по недоступному адресу — `/healthz` отвечает
`database: fail` через ~8 с; `TG_API_ID=abc` — контейнер жив, в логе имя переменной.

## Первый живой запуск на Amvera

- Контейнер не стартовал из-за спецсимволов в `WEB_SECRET_KEY` (ответ поддержки Amvera):
  значения переменных на Amvera — только латиница и цифры.
- Следующая ошибка — `DATABASE_URL`: в пароле базы был `/`, `#` или `?`, адрес
  разбирался неправильно, а asyncpg писал в лог начало пароля. Добавлена проверка
  `pool.dsn_problem()`: понятное сообщение без самой строки; супервизор со сломанной
  строкой держит админку, а bot и collector не запускает и раз в 5 минут повторяет причину.
  Владельцу: сменить пароль базы на буквы и цифры (кусок старого попал в лог).
- `Network is unreachable` при подключении к базе — прямой хост Supabase
  (`db.….supabase.co`, только IPv6). Супервизор теперь предупреждает об этом в логе;
  нужна строка Session pooler.
- Виджет входа «Username invalid»: `BOT_USERNAME` теперь очищается от `@`, ссылки
  `t.me/…` и пробелов; все строковые переменные обрезаются по краям.

## Приватность БД (сделано попутно)

Supabase по умолчанию отдаёт таблицы схемы `public` через PostgREST под ролями
`anon`/`authenticated`, то есть по publishable-ключу, который публичен по своей природе.
Для базы с перепиской закрытой группы это прямое нарушение TZ §9. В `schema.sql` добавлен
блок: RLS без политик на всех 14 таблицах + снятие грантов у публичных ролей (блок
пропускается на обычном Postgres, где таких ролей нет). Проверено на живом проекте:
REST отвечает `401 permission denied` и на чтение, и на запись; 60 тестов приложения
проходят — процессы ходят под ролью-владельцем, на неё RLS не действует.

## Названия групп, новый дизайн, понятные настройки, страница участников (сделано)

Запрос владельца: объяснить «профиль интересов», адаптировать кабинет под телефон,
сделать страницу, где участники группы (и только они) смотрят дайджесты и рейтинги без
права что-то менять, красивый дизайн и графики, настоящие названия групп и понятные
названия настроек — ничего не сломав.

**Названия групп.** Группа из `TG_GROUP_ID` заводилась одним id, поэтому везде был номер.
Теперь название подтягивают коллектор (при старте и при переименовании группы) и бот (при
старте и раз в сутки, `getChat` — только чтение). `repo.set_chat_title` не затирает
название пустым. Уже собранные дайджесты показываются и публикуются с нынешним названием
(`DigestData.titled`). Пока название неизвестно — «Группа -100…», а не голый номер.

**Дизайн.** Всё переписано поверх одной системы токенов (светлая и тёмная тема — свои
шаги цвета, контраст текста проверен: ≥ 7:1 основной, ≥ 5:1 приглушённый). На телефоне —
нижняя панель «Обзор · Дайджесты · Рейтинги · Группы · Ещё», на компьютере — боковое
меню. Таблицы на телефоне стали карточками или прокручиваются с закреплённой первой
колонкой; режимы на узком экране — список вариантов с галочкой. Графики (Chart.js) — по
правилам dataviz: одна серия одним цветом без легенды, тонкие столбцы со скруглённым
концом, тонкая сетка, одна подпись у максимума, подсказка при наведении и таблица под
каждым графиком. htmx и Chart.js лежат в репозитории (`src/web/static/vendor`, с
лицензиями): из российских сетей CDN бывает не видно. Заголовки безопасности:
`X-Frame-Options: DENY`, `Referrer-Policy: same-origin`, `Cache-Control: no-store` на
страницах с содержимым групп.

**Понятные названия.** `src/web/labels.py` — одно место для всех подписей: «Польза»,
«Живое обсуждение», «Конкретика», «Совпадение с интересами», «Новизна», «Ваше участие»
вместо `w_*`; «Ссоры и перепалки», «Приглушённые участники», «Повтор без нового» вместо
штрафов; «Строгость отбора» вместо порога; у каждого — пояснение. Веса — ползунками.
Процессы на «Обзоре» и в «Системе» — «работает / молчит / готово / идёт» с «3 мин назад».
Расходы на модель считаются по `LLM_PRICE_IN` / `LLM_PRICE_OUT` (было зашито старое
$0.028 / $0.42 — занижало расходы в несколько раз).

**Страница участников** (`/g`, `src/web/portal.py`, решение владельца записано в TZ §9).
Режим `chats.portal`: `off` (по умолчанию) · `digests` · `all` (плюс рейтинги), включается
в «Группах» с подтверждением. Участник входит той же кнопкой Telegram; кука участника
годится только для `current_viewer` — админку по-прежнему открывает лишь совпадение uid с
`OWNER_ID` на каждом запросе. Членство (`src/web/membership.py`): сначала Bot API
`getChatMember` («удалён» — не пускать никогда), если Telegram не может ответить или
говорит «не состоит» — свежий (≤ 24 ч) список участников коллектора, иначе не пускать.
Ответ помнится 10 минут («да») и минуту («нет»). Коллектор сверяет список раз в 6 часов
(`src/collector/members.py`, только id, без имён) и обновляет по событиям входа и выхода;
неполный или скрытый список старых участников не выкидывает. Показывается то же, что
увидела бы группа: дайджест карточками без оценок, признаков и кнопок обучения, график
активности, рейтинги только из позитивных номинаций и без скрывшихся по /optout. Чего
нельзя — 404 без названия группы. Владелец может посмотреть страницу закрытой группы
заранее (с пометкой «закрыта»).

**Проверено:** 600 тестов (+87: доступ к каждой странице админки с кукой участника,
мутации, закрытый режим, вышедший участник, экранирование, `javascript:`-ссылки,
порядок источников членства, кэш, сверка участников, названия). Живой прогон на локальной
базе с подставным Bot API: участник входит и видит `/g/1`, «вышедший» и «удалённый» —
без куки, «вышедший», которого коллектор видит в группе, — пускается, удалённый — нет
даже при наличии в списке; в подставной Bot API ушли только `getChatMember`. Скриншоты
всех страниц на 390 и 1280 px, светлая и тёмная тема, без горизонтальной прокрутки.

**Решения, которых не было в запросе явно:**
1. «Общедоступная» страница сделана не публичной, а по входу через Telegram: иначе нельзя
   проверить, что человек состоит в группе, — именно этого владелец и просил.
2. Рейтинги на странице участников — отдельный режим, а не «Рейтинг недели в группе»:
   владелец может показывать рейтинг на сайте, не публикуя его каждое воскресенье в чат.
3. Ссылку на страницу бот в группу не отправляет — админка показывает её владельцу.
